# 第 12 周：测试、调试与持续集成

本周目标是把“我点过了，看起来能用”升级为可重复验证的工程证据。你会练习前端单元测试、接口与后端集成测试、Playwright 端到端测试、系统化调试，以及最小权限的 CI。

开始前请确保你已经能启动 IssueFlow，并能说清三种数据模式：浏览器本地模式、同源 D1/R2 API、独立 .NET API。本周不要求同时修改三种实现；测试时必须明确记录当前模式。

本周产出：一份测试地图、至少 3 个由你独立完成的自动化测试、一份缺陷调查记录、一条可重复执行的全套验证命令，以及一份 CI 运行证据。

> 时间规则：表格中的分钟数都是主动学习时间。安装依赖、等待构建、等待 CI runner 或等待浏览器下载的空闲时间不计入 120 分钟；等待时可以阅读失败日志、整理测试矩阵或补写实验记录，做了这些才计时。

## Day 78：建立测试地图与第一个边界测试 {#day-78}

### 今天要解决的问题

- 单元测试、集成测试和端到端测试各自应该保护什么？
- 什么样的测试失败能够准确指出问题，而不是只告诉你“页面坏了”？
- 如何先看到测试失败，再写最小实现让它通过？

### 120 分钟任务

| 时间         | 主动任务                                                                                | 当段产出           |
| ------------ | --------------------------------------------------------------------------------------- | ------------------ |
| 0–15 分钟    | 阅读 `frontend/package.json` 的测试脚本，并定位现有 `*.test.ts` 与 `*.spec.ts`          | 实际可运行命令清单 |
| 15–35 分钟   | 阅读 `frontend/src/features/issues/types.test.ts` 或同类测试，标注 Arrange、Act、Assert | 一段测试结构注释   |
| 35–70 分钟   | 选择一个纯函数或数据转换，先添加一个会失败的边界用例，再做最小修正                      | 红灯与绿灯各一次   |
| 70–105 分钟  | 不看答案，独立补充第二个边界用例；运行相关测试和类型检查                                | 独立测试与通过输出 |
| 105–120 分钟 | 画出当前仓库测试地图并写 5 句复盘                                                       | 测试地图与日记     |

### 必要概念

- 单元测试适合纯函数、格式化、映射、筛选和边界规则。
- 好测试只因一个清晰原因失败，名称应描述输入、行为和结果。
- 测试优先保护行为，不把内部变量名、临时 DOM 层级或实现顺序写死。
- 泛型只能帮助编译期检查；来自网络或 JSON 的值仍需要运行时验证或可靠的边界处理。

### 动手实验

1. 从 Issue 的状态、优先级、分页或查询参数转换中选择一个小目标。
2. 写一个正常输入用例和一个边界输入用例，例如空值、未知枚举、页码边界或重复标签。
3. 故意让断言错一次，确认错误信息能指出哪个行为不符合预期。
4. 恢复正确断言，保存测试输出。

### 独立任务

在不复制现有测试主体的前提下，再设计一个“未来重构时最可能被破坏”的用例。先在日记里写出预期，再运行测试。若测试一开始就通过，也要解释它保护了什么。

### 验收证据

- 测试地图：列出至少 3 个前端单元测试入口、1 个后端测试入口和 1 个 E2E 入口。
- 新增测试的文件路径、测试名称和一次通过输出。
- 一次有意制造的失败输出，能够看出期望值与实际值。
- 3–5 句话解释为什么这个用例属于单元测试。

## Day 79：测试数据边界与 API 客户端行为 {#day-79}

### 今天要解决的问题

- `fetch` 收到 4xx/5xx 时为什么不会自动进入网络异常分支？
- API 客户端怎样区分 JSON、空响应体和 Problem Details？
- Mock 应该停在哪个系统边界，才不会把实现本身一起 Mock 掉？

### 120 分钟任务

| 时间         | 主动任务                                                             | 当段产出       |
| ------------ | -------------------------------------------------------------------- | -------------- |
| 0–15 分钟    | 复习 Day 78，并阅读 `frontend/src/api/issueflowApi.ts` 的请求封装    | 请求流程图     |
| 15–35 分钟   | 列出成功、204、400、401、404、409、非 JSON 与网络中断七类结果        | 响应矩阵       |
| 35–75 分钟   | 用可控的 `fetch` 响应完成一个成功用例和一个 Problem Details 失败用例 | 两个自动化测试 |
| 75–105 分钟  | 独立添加 204 或非 JSON 响应用例，避免对空响应调用 `json()`           | 独立边界测试   |
| 105–120 分钟 | 运行测试、类型检查并记录 Mock 的边界                                 | 通过证据与反思 |

### 必要概念

- 网络错误和 HTTP 错误不是同一件事；只有前者通常会让 `fetch` Promise reject。
- `response.ok`、HTTP 状态、`content-type` 和响应体需要分别判断。
- 测试客户端时可以替换网络边界，但仍应运行真实的解析、错误映射和返回值逻辑。
- 不要只断言“抛错了”；还要断言状态码、用户可理解的信息和字段错误是否保留。

### 动手实验

1. 为请求封装画出“请求 → 状态检查 → 内容类型 → JSON/空体 → 返回或抛错”的流程。
2. 构造一个成功 JSON 响应，确认结果 shape。
3. 构造一个带 `errors` 的 400 Problem Details，确认前端错误对象保留字段信息。
4. 清理 Mock，确认一个测试的网络状态不会泄漏到下一个测试。

### 独立任务

从 204、401、409、非 JSON 服务器错误中任选一个未被现有测试覆盖的分支，独立补测试。若实现不符合合理预期，先保留失败测试，写出最小修复方案，再决定是否改实现。

### 验收证据

- 一张至少 7 行的响应矩阵。
- 测试文件路径及两个不同状态的测试名称。
- 相关测试与类型检查的通过输出。
- 一段说明：你 Mock 了什么、没有 Mock 什么、为什么。

## Day 80：用 Playwright 验证真实用户旅程 {#day-80}

### 今天要解决的问题

- 单元测试全部通过时，为什么真实页面仍可能失败？
- 如何选择稳定的角色、标签和文本定位，而不是脆弱的 CSS 层级？
- 怎样让 E2E 在可重复的数据状态下运行？

### 120 分钟任务

| 时间         | 主动任务                                                       | 当段产出       |
| ------------ | -------------------------------------------------------------- | -------------- |
| 0–15 分钟    | 阅读 `frontend/e2e/issue-lifecycle.spec.ts` 及 Playwright 配置 | 用户旅程步骤表 |
| 15–35 分钟   | 启动测试所需服务，确认当前数据模式和基线数据                   | 环境记录       |
| 35–70 分钟   | 运行一条现有旅程，阅读 trace、截图或失败附件                   | 一次可解释运行 |
| 70–105 分钟  | 独立增加一个用户可观察断言或异常路径，不依赖固定等待           | 新的 E2E 保护  |
| 105–120 分钟 | 重跑目标用例并写稳定性复盘                                     | 两次运行证据   |

### 必要概念

- E2E 保护浏览器、路由、状态、网络和 UI 的组合行为，数量应少而关键。
- 优先按可访问角色和名称定位；`data-testid` 只用于缺少稳定语义的情况。
- 禁止用任意长的固定 sleep 掩盖竞态；等待用户可观察的状态或明确的响应。
- 测试必须说明使用 local、同源 API 还是 .NET API，不能让运行结果靠猜。

### 动手实验

1. 选择“登录后打开列表 → 创建或编辑 Issue → 在详情中看到结果”中的一条关键旅程。
2. 先逐步执行并记录每一步的用户可观察结果。
3. 运行无头测试；若失败，打开 trace 定位第一个偏离预期的步骤。
4. 用角色/名称定位替换一处脆弱选择器，连续运行两次。

### 独立任务

为旅程添加一个异常路径，例如必填字段、非法附件、未授权写操作或请求失败。测试应断言用户看到可行动的信息，并且页面没有悄悄丢失已有输入。

### 验收证据

- 当前数据模式、启动命令和测试命令。
- 一条 trace、截图或 Playwright 报告路径。
- 新断言的测试名称及连续两次通过结果。
- 定位策略对比：原选择器为什么脆弱，新选择器为什么更接近用户。

## Day 81：从症状到根因的系统调试 {#day-81}

### 今天要解决的问题

- 如何避免一看到报错就随机修改代码？
- Console、Network、React 状态、服务端日志和测试 trace 分别回答什么问题？
- 怎样证明修复的是根因而不是暂时隐藏症状？

### 120 分钟任务

| 时间         | 主动任务                                          | 当段产出       |
| ------------ | ------------------------------------------------- | -------------- |
| 0–15 分钟    | 建立独立学习分支，记录干净基线和复现步骤          | 缺陷调查单     |
| 15–35 分钟   | 制造一个可恢复的小故障，先预测它会在哪一层出现    | 假设与预测     |
| 35–65 分钟   | 用 Console、Network 或 trace 收集事实，不修改代码 | 时间线与证据   |
| 65–95 分钟   | 缩小到最小根因，添加回归测试并完成最小修复        | 失败测试与修复 |
| 95–110 分钟  | 运行相邻测试，确认没有只修好单一路径              | 回归结果       |
| 110–120 分钟 | 写五段式调试记录                                  | 可复用调试手册 |

### 必要概念

调试顺序固定为：稳定复现 → 缩小范围 → 提出可证伪假设 → 收集事实 → 最小修复 → 回归验证。一个好的调查记录要区分“观察到的事实”和“我认为的原因”。

### 动手实验

在学习分支中制造一个容易恢复的故障，例如错误查询参数、错误枚举映射、漏掉 `response.ok` 判断或状态更新遗漏。不要删除用户已有改动，不使用 `git reset --hard`。按以下层次定位：

1. 页面症状和复现频率。
2. Network 中的请求 URL、状态、响应体与耗时。
3. 前端错误映射或状态更新路径。
4. 如果请求到达后端，再看服务端日志与 `traceId`。
5. 用自动化测试固定根因。

### 独立任务

关闭教程内容，只根据你的调查单重新复现和修复一次。然后向“昨天的自己”解释：哪个证据排除了另外两个看似合理的原因？

### 验收证据

- 缺陷标题、环境、复现步骤、期望、实际、频率。
- 至少两条事实证据和一个被否定的假设。
- 修复前失败、修复后通过的同一条自动化测试。
- 改动文件列表与一段根因说明。

## Day 82：契约、权限与安全负面测试 {#day-82}

### 今天要解决的问题

- 为什么只测 200 成功响应不能证明 API 可靠？
- 400、401、403、404、409 各自表达什么？
- 文件上传、Cookie、CORS 和字段校验应该如何留下可重复证据？

### 120 分钟任务

| 时间         | 主动任务                                              | 当段产出     |
| ------------ | ----------------------------------------------------- | ------------ |
| 0–20 分钟    | 阅读后端集成测试入口与 Issue/Auth/Attachment 相关测试 | 负面路径清单 |
| 20–40 分钟   | 建立“输入—状态—Problem Details—前端行为”契约矩阵      | 契约矩阵     |
| 40–75 分钟   | 运行后端目标测试，追踪一个 4xx 从 Endpoint 到前端错误 | 跨层链路图   |
| 75–105 分钟  | 独立补充一个权限、校验或上传安全用例                  | 新的负面测试 |
| 105–120 分钟 | 运行回归并记录测试数据库/附件隔离方式                 | 安全证据     |

### 必要概念

- 认证回答“你是谁”，授权回答“你能做什么”，CORS 限制浏览器跨源读取；三者不能互相替代。
- 测试 401 时不要期待 HTML 登录重定向；API 应返回可解析的错误契约。
- 文件名、扩展名、MIME 和文件签名是不同信号；任何客户端字段都不能直接当作可信事实。
- 测试应使用临时数据库和上传目录，不污染日常 `issueflow.db` 或真实文件。

### 动手实验

从以下路径选择一条：匿名写操作、非法枚举、重复标题、伪造文件、超大文件、不允许的 Origin。先写出预期 HTTP 状态和错误字段，再运行现有测试或发送隔离请求，核对实际结果。

### 独立任务

补一个现有测试集没有明确保护的负面用例。测试名称必须包含条件和预期，不允许只断言“不是 200”。若前后端实现行为不同，在记录中区分 shape contract、错误 contract 和行为 contract。

### 验收证据

- 至少包含 400、401、404、409 的契约矩阵；能产生 403 时也要记录。
- 新负面测试的文件、名称和通过输出。
- 测试使用临时数据/附件位置的说明。
- 一段安全结论：该测试阻止了什么风险，仍没有覆盖什么。

## Day 83：设计最小权限的 CI {#day-83}

### 今天要解决的问题

- 本地通过为什么不等于主分支安全？
- CI 应该按什么顺序运行安装、格式、类型、测试和构建？
- 如何避免让拉取请求获得不需要的写权限或部署权限？

### 120 分钟任务

| 时间         | 主动任务                                                           | 当段产出     |
| ------------ | ------------------------------------------------------------------ | ------------ |
| 0–20 分钟    | 阅读现有 `.github/workflows` 与前后端脚本，不假设命令名            | 现状流程图   |
| 20–40 分钟   | 设计前端与 .NET 的必需检查、依赖缓存和失败顺序                     | CI 草图      |
| 40–70 分钟   | 在本地按 CI 顺序执行可运行检查，记录真实耗时                       | 本地基线     |
| 70–100 分钟  | 完成 `day-83-learning-ci.yml`：最小权限、真实命令、缓存与 artifact | 可审查工作流 |
| 100–120 分钟 | 阅读一次运行日志，把首个失败定位到具体命令                         | CI 调查记录  |

### 必要概念

- 默认只授予 `contents: read`；只有真正部署的 job 才需要额外权限。
- 普通 PR 做构建和测试，不应发布站点、写仓库或接触生产 secrets。
- 缓存是优化，不是正确性的前提；`npm ci` 与 lockfile 才提供可重复依赖。
- 将最快、最确定的检查放前面，可以更早反馈；E2E 通常放在构建和单元测试之后。
- 等待 runner 或下载依赖不计学习时间。等待时阅读前一个失败日志或补测试地图。

### 动手实验

写出一条最小 CI 流程：checkout → 固定运行时 → 安装锁定依赖 → 类型/单测 → 构建 → 后端测试 → 关键 E2E。根据仓库实际脚本删去不存在的命令，不得凭空发明脚本。

检查以下风险：是否使用 `pull_request_target`，是否在顶层给了写权限，是否上传了整个仓库，是否在日志输出环境变量，是否让失败步骤被 `continue-on-error` 隐藏。

### 独立任务

先运行 `npm run learn:create -- 83` 生成 `.github/workflows/day-83-learning-ci.yml`，再把红灯支架改成真正执行仓库现有命令的最小权限工作流。即使生产 CI 已经合理，也要完成这份隔离的学习工作流；审查报告可以说明“生产工作流无需修改”，但不能代替当日实现。

### 验收证据

- CI 流程图与每个步骤保护的风险。
- 一次按 CI 顺序执行的本地输出和耗时表。
- 完成的 `.github/workflows/day-83-learning-ci.yml`、本地等价命令输出，以及可用时的运行链接/截图。
- 权限说明：PR job 与 deploy job 各需要什么、明确不需要什么。

## 过关标准

- 120 分钟记录均为主动学习时间，等待时间已暂停或转为有产出的任务。
- 能用自己的话区分单元、集成和 E2E，并为一个行为选择合适层级。
- 至少一次展示“先失败、后通过”的同一条回归测试。
- 能从 Network/trace/日志找到第一处异常，而不是靠随机改代码。
- 自动化检查覆盖至少一个失败响应或安全负面路径，不能只有 200 happy path。
- CI/流程审查没有给普通 PR 不必要的写入、部署或 secret 权限。
- 前端类型检查、目标单测、后端目标测试和关键 E2E 均有可定位证据。
- 任一项未达标时，不以总时长抵消；按 `assessments.md` 的 W12 补救路线完成后再进入毕业项目。
