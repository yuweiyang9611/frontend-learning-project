# 第 13 周：毕业项目与可验证交付

本周把前 12 周的知识压缩成一个小而完整的纵向切片。推荐题目是“Issue 健康摘要”：显示总数、各状态数量、未分配数量和逾期数量，并能从摘要进入对应筛选结果。也可以选择同等规模的功能，但不得通过堆页面或复制现有代码扩大范围。

默认交付范围是：TypeScript 契约、至少一种真实数据路径、加载/空/错误状态、键盘和读屏可用、自动化测试、文档与演示证据。若实现三种数据模式，必须记录它们的行为差异，不能声称完全等价。

本周产出：一页项目章程、一份契约表、一个可运行的纵向功能、测试与安全证据、最终演示包和毕业自评。

> 毕业项目重视可验证的小闭环。等待安装、构建、部署或 CI 的空闲时间不计入 120 分钟；暂停计时，或利用等待时间检查日志、补充契约和整理证据。

## Day 85：冻结问题、范围与验收标准 {#day-85}

### 今天要解决的问题

- 用户遇到的具体问题是什么，而不是“我要加一个很酷的功能”？
- 14 小时内的最小纵向切片包含哪些内容？
- 哪些想法明确不在本周范围内？

### 120 分钟任务

| 时间         | 主动任务                                       | 当段产出     |
| ------------ | ---------------------------------------------- | ------------ |
| 0–20 分钟    | 浏览当前 IssueFlow 页面与源码，记录真实痛点    | 问题观察表   |
| 20–40 分钟   | 写用户故事、成功指标和非目标                   | 一页项目章程 |
| 40–65 分钟   | 画 UI → API client → 实现 → 存储的数据路径     | 系统切片图   |
| 65–95 分钟   | 定义 TypeScript shape、HTTP/本地契约与错误状态 | 契约草案     |
| 95–110 分钟  | 把工作拆成 Must/Should/Could，估计每天上限     | 7 天看板     |
| 110–120 分钟 | 做范围挑战并冻结 Must                          | 范围承诺     |

### 动手实验

以“Issue 健康摘要”为例，先用纸面数据计算：总数、`open`/`in_progress`/`resolved` 数量、未分配数量、已过截止日且未解决数量。写清截止日以哪个时区和日期为准，并确认各计数是否互斥。

项目章程至少包含：用户、问题、一个成功场景、一个失败场景、一个无数据场景、非目标、风险和验收证据。

### 独立任务

删除至少一个“看起来不错但不是闭环必需”的功能。用一句话解释删除它如何降低契约、测试或无障碍风险。未经重新估算，不在后续偷偷加回。

### 验收证据

- 一页项目章程与数据路径图。
- Must/Should/Could 清单，Must 不超过 5 项。
- 初版 TypeScript/JSON shape 和至少 3 个错误或边界场景。
- 一个明确删除的范围项及理由。

## Day 86：先完成 TypeScript 领域模型和纯逻辑 {#day-86}

### 今天要解决的问题

- 如何让数据 shape 在编译期可读，又不把网络 JSON 当作自动可信？
- 哪些业务规则可以先写成纯函数，从 UI 和后端中抽离？
- 日期、可空字段和枚举怎样避免含糊？

### 120 分钟任务

| 时间         | 主动任务                                         | 当段产出        |
| ------------ | ------------------------------------------------ | --------------- |
| 0–15 分钟    | 复核项目章程与现有 Issue/Member 类型             | 类型复用清单    |
| 15–40 分钟   | 定义最小请求/响应/视图模型，标出 null 与省略差异 | TypeScript 契约 |
| 40–75 分钟   | 用纯函数实现摘要计算或响应映射，先写边界测试     | 红绿测试循环    |
| 75–105 分钟  | 独立覆盖时区、空数组、未知值或重复项中的两个边界 | 独立测试        |
| 105–120 分钟 | 运行类型检查并做一次“删除 `any`”审查             | 类型证据        |

### 必要概念

- 后端 `long` 映射到 TypeScript `number` 时要考虑安全整数范围。
- 日历日期与时间点不同；`YYYY-MM-DD` 不应随意套用本地时区转换。
- `null`、属性省略和空集合表达不同语义。
- `request<T>()` 的 `T` 是开发者声明，不是运行时验证。
- 派生视图模型应说明来源，避免 UI 重复计算不同版本的业务规则。

### 动手实验

先写一组固定 Issue 数据，不连接页面和真实 API。实现摘要计算并覆盖：空集合、逾期边界当天、已解决但截止日已过、无负责人。每个测试名称都应包含输入条件和结果。

### 独立任务

从你的契约中选一个最容易误用的字段，制作一个错误示例，证明 TypeScript 或运行时边界能够拦截它。如果拦不住，记录原因并增加最小保护。

### 验收证据

- 契约文件路径与字段说明表。
- 至少 3 个纯逻辑测试，包含空数据和一个日期/可空边界。
- 类型检查通过输出。
- 项目新增代码中不存在无解释的 `any`、双重断言或忽略类型错误。

## Day 87：接通一种真实数据路径 {#day-87}

### 今天要解决的问题

- 新功能的 canonical contract 在哪里？
- local、同源 D1/R2、独立 .NET API 哪一种是本次必交实现？
- 请求失败时如何保持错误 shape 和可追踪性？

### 120 分钟任务

| 时间         | 主动任务                                         | 当段产出        |
| ------------ | ------------------------------------------------ | --------------- |
| 0–20 分钟    | 选择并写明本次必交数据模式，核对现有请求封装     | 模式决策记录    |
| 20–45 分钟   | 完成客户端方法及成功/失败契约测试                | API client 证据 |
| 45–80 分钟   | 完成所选真实实现或适配层，沿用现有验证与错误规范 | 可调用数据路径  |
| 80–105 分钟  | 独立处理一个 400/401/404/500 或数据异常路径      | 负面路径        |
| 105–120 分钟 | 对照契约表抓取一次真实响应并修正偏差             | 契约对照        |

### 动手实验

先明确模式：

- `local`：浏览器本地数据，适合先证明交互，但不能冒充服务器持久化；
- API Base URL 为空：同源 API，数据可落到 D1/R2；
- API Base URL 指向 .NET：独立 .NET API 与 SQLite/文件存储。

只选择一种作为 Must，其他模式列为兼容性检查或 Should。真实响应应与 Day 86 的契约逐字段核对。若返回 Problem Details，保留状态、标题、详情、字段错误和可用的 `traceId`。

### 独立任务

关闭服务、制造未授权或构造非法输入，选择一种失败方式。页面尚未接入也没关系，但客户端层必须返回可区分的错误，而不是空数组或伪成功。

### 验收证据

- 必交数据模式和选择理由。
- 一次真实成功响应与一次真实失败响应，隐去 Cookie、token 和个人信息。
- 客户端契约测试及实现层目标测试。
- 三种模式兼容矩阵：已验证、未验证、已知差异，不写“应该一样”。

## Day 88：接入 UI 状态与无障碍交互 {#day-88}

### 今天要解决的问题

- 页面如何区分首次加载、刷新、空数据、局部失败和成功？
- 摘要卡片是按钮、链接还是纯文本？
- 键盘和读屏用户怎样知道筛选已经变化？

### 120 分钟任务

| 时间         | 主动任务                                     | 当段产出     |
| ------------ | -------------------------------------------- | ------------ |
| 0–15 分钟    | 画加载、成功、空、错误四态线框               | 状态草图     |
| 15–40 分钟   | 将数据请求接入现有页面结构，避免复制全局状态 | 最小 UI 切片 |
| 40–70 分钟   | 实现语义化摘要和进入筛选结果的交互           | 可操作界面   |
| 70–100 分钟  | 仅用键盘完成旅程，并检查名称、焦点与状态提示 | 无障碍修正   |
| 100–120 分钟 | 独立实现错误后的重试且不丢失当前上下文       | 恢复路径     |

### 必要概念

- 可点击的摘要应使用真实 `button` 或 `a`，不要给 `div` 补一个点击事件假装控件。
- 颜色不能是唯一状态信号；数字、名称和当前筛选都要有文本表达。
- 加载反馈不应让布局剧烈跳动；错误信息应告诉用户下一步。
- 更新筛选后，要让可见标题、结果数量或 live region 提供可感知反馈。

### 动手实验

断网或让请求失败，确认页面能从加载进入错误并重试；返回空数据，确认不是永远显示骨架屏；恢复成功，确认摘要与列表筛选一致。最后用 Tab、Shift+Tab、Enter/Space 完成相同旅程。

### 独立任务

不使用鼠标，从页面入口进入你的功能、选择一个摘要、确认结果、返回并重试失败状态。记录第一处阻塞，完成最小修复后再走一遍。

### 验收证据

- 四态截图或短视频，至少包含错误和空状态。
- 完整键盘旅程步骤及焦点顺序。
- 语义/可访问名称检查结果。
- 摘要数字与列表结果一致的手工或自动化证据。

## Day 89：安全、隐私与可靠性审查 {#day-89}

### 今天要解决的问题

- 新功能引入了哪些输入、身份、跨源或信息泄露风险？
- “只读统计”为什么仍需校验和授权决策？
- 日志、截图和错误信息怎样避免泄露凭据？

### 120 分钟任务

| 时间         | 主动任务                                   | 当段产出     |
| ------------ | ------------------------------------------ | ------------ |
| 0–20 分钟    | 为功能画信任边界，列出用户输入、网络与存储 | 小型威胁模型 |
| 20–45 分钟   | 检查认证/授权、CORS、字段校验和错误详情    | 安全审查表   |
| 45–75 分钟   | 增加一个安全或可靠性负面测试               | 防回归测试   |
| 75–100 分钟  | 检查错误 UI、日志和证据中是否含敏感数据    | 脱敏结果     |
| 100–120 分钟 | 独立处理一个超时、重复请求或过期数据问题   | 恢复策略     |

### 动手实验

至少验证以下三项：匿名访问是否符合现有策略；非法查询不会变成成功响应；错误信息不会返回堆栈、数据库路径或凭据。若功能不需要认证，也要写出这是继承现有公开读取策略，而不是忘记授权。

### 独立任务

假设请求被快速点击两次、较慢请求后返回或页面已切换筛选。选择一个竞态，复现并通过禁用、取消、请求身份或幂等设计处理。说明为什么选择该方法。

### 验收证据

- 一页信任边界和至少 5 条风险/控制对照。
- 一个负面测试的失败前/通过后证据。
- 脱敏后的日志或响应；不得提交 Cookie、token、连接串和真实个人数据。
- 一段剩余风险说明，不能写“没有风险”。

## Day 90：建立毕业级测试与 CI 证据 {#day-90}

### 今天要解决的问题

- 哪几条测试最能证明纵向切片，而不是追求测试数量？
- 如何证明类型、契约、UI 和真实旅程彼此一致？
- CI 失败时交付物还能否被审阅？

### 120 分钟任务

| 时间         | 主动任务                             | 当段产出     |
| ------------ | ------------------------------------ | ------------ |
| 0–15 分钟    | 按风险排列测试缺口                   | 风险测试矩阵 |
| 15–45 分钟   | 完成纯逻辑与客户端契约测试           | 快速测试层   |
| 45–75 分钟   | 完成实现层集成测试或等价真实数据测试 | 数据层证据   |
| 75–100 分钟  | 完成一条关键 E2E，覆盖用户可观察结果 | 旅程证据     |
| 100–120 分钟 | 按 CI 顺序执行，整理失败与 artifact  | 质量闸门     |

### 动手实验

用一条垂直线连接同一规则的证据：TypeScript 类型 → 纯函数/解析测试 → API 响应 → UI 状态 → E2E 断言。若其中一层没有必要，写理由；不能只因为难写而跳过。

### 独立任务

故意改变一个摘要规则或错误字段，让至少一条测试失败。确认错误指向真实契约，再恢复实现并重跑。若没有任何测试失败，说明测试没有保护这条规则，需要补强。

### 验收证据

- 风险测试矩阵及至少三层自动化证据。
- 同一规则的一次有意失败和恢复通过记录。
- 类型检查、构建、相关测试与关键 E2E 的结果。
- CI 链接/截图；若 CI 环境不可用，提交逐条等价本地命令、环境和输出。

1. 项目章程、范围承诺、数据路径图和契约表。

## 过关标准

- Must 范围全部完成；Should/Could 未完成不影响通过，但必须如实记录。
- 功能解决项目章程中的具体问题，且数据结果可与固定样本人工核对。
- TypeScript 契约没有用无解释的 `any`、忽略错误或双重断言绕过。
- 至少一种真实数据路径通过，其他模式没有被错误宣称为等价。
- 加载、空、错误、重试和键盘旅程均有证据。
- 至少三层测试保护同一纵向规则，并出现过一次有意义的红灯到绿灯。
- 安全审查覆盖身份/权限决策、输入校验、错误信息和证据脱敏。
- 100 分毕业量表达到通过线，且 TypeScript、Contract、安全任一项为 0 时直接不通过。
- 所有等待时间已从 120 分钟主动学习统计中排除。
