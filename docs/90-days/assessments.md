# 评估、检查点与毕业标准

评估的作用不是给观看时长打分，而是确认你能否在没有逐步答案时预测、实现、验证并解释。所有分数都必须附可定位证据；没有证据的项目按 0 分处理。

## 评分原则

1. 只评价本人完成并能解释的工作。复制后能运行但不能解释，最高只能算“在指导下完成”。
2. 测试输出、HTTP 响应、截图、trace、分支和提交是证据；“我记得通过了”不是证据。
3. 自动化通过不自动等于满分，还要看测试是否保护真实行为、是否覆盖边界。
4. 一次失败不是扣分理由；能保存失败、定位根因、完成回归反而是强证据。
5. 提示可以使用，但必须记录等级，并在关闭提示后完成一个相邻任务。
6. 任何证据含 secrets、真实个人数据或他人未授权内容时，该证据无效，并先完成安全清理。
7. TypeScript、Contract、安全是毕业硬门槛，任一项为 0 时，无论总分多高都不毕业。

## 通用 0–4 等级

| 分数 | 表现                                             | 证据特征                           |
| ---: | ------------------------------------------------ | ---------------------------------- |
|    0 | 未做、无法运行、证据缺失，或描述与真实实现矛盾   | 无可复查证据                       |
|    1 | 跟随复制，离开步骤无法重现或解释                 | 只有最终截图，没有过程             |
|    2 | 在明确提示下完成主要步骤，边界和原因不清楚       | 有运行结果，但独立迁移失败         |
|    3 | 能独立完成核心任务、处理常见失败并解释数据流     | 有提交、测试和复盘                 |
|    4 | 能独立迁移到新输入，覆盖边界，说明取舍和剩余风险 | 红绿测试、负面路径、可交接证据完整 |

## 每周 20 分量表

每周按五个维度各打 0–4 分。每个分数后写一个证据链接、文件路径、测试名称或提交 ID。

| 维度           | 0 分                         | 2 分                 | 4 分                                                    |
| -------------- | ---------------------------- | -------------------- | ------------------------------------------------------- |
| 概念与源码理解 | 无法指出入口或数据流         | 能跟随说明主要文件   | 能独立追踪输入、状态、输出和失败路径，并纠正错误预测    |
| 动手实验       | 未运行                       | 在步骤指导下运行     | 修改输入、观察差异并保存可重复结果                      |
| 独立迁移       | 未做独立任务                 | 依赖 2–3 级提示完成  | 关闭步骤后完成相邻需求，能解释为何有效                  |
| 验证与调试     | 只凭页面观感                 | 有一条测试或手工检查 | 有针对风险的自动化、负面用例和根因记录                  |
| 工程责任       | 覆盖改动、泄露数据或绕过检查 | 基本使用分支和类型   | 分支/提交清晰，类型、契约、安全、无障碍按当周内容有证据 |

### 每周判定

- **通过：16–20 分**，且没有维度为 0；可以进入下一周。
- **条件通过：12–15 分**，且没有安全事故；先在 7 天内完成一项指定补救和补测。
- **未通过：0–11 分**，或任一维度为 0，或独立任务/验收证据缺失；暂停新课。
- 时长不能补偿缺失能力。完成 840 分钟但没有独立任务，仍不能通过该周。

## 阶段检查点的 0–5 等级

W4、W7、W10、W11、W12 每个检查点有五项，每项 0–5 分，总分 25。评分含义：

- 0：没有证据，或实现/表述明显错误；
- 1：复制结果，不能独立运行；
- 2：在逐步提示下完成部分 happy path；
- 3：独立完成核心路径并能解释；
- 4：覆盖一个重要边界，有自动化或可重复诊断证据；
- 5：能迁移、比较方案、解释取舍与剩余风险，证据可交给别人复现。

检查点通过线为 **18/25**，且所有标记为硬门槛的项目至少 2 分。未通过只补对应薄弱项，不要求重做全部四周。

## W4 检查点：前端基础能否形成可用页面

### 限时任务

在不照抄完整答案的情况下，为一个活动报名表完成语义结构、响应式样式和 JavaScript/DOM 行为。允许阅读源码和官方文档，使用提示必须记录等级。本检查点不得要求第 5 周才介绍的 TypeScript。

| 项目                                 | 分值 | 通过证据                                                  |
| ------------------------------------ | ---: | --------------------------------------------------------- |
| 语义 HTML 与表单                     |   /5 | 标签、按钮、输入、错误关联合理；不用可点击 `div` 代替控件 |
| CSS 与响应式                         |   /5 | 小屏和宽屏均可用，焦点可见，颜色不是唯一信息              |
| JavaScript/DOM 行为（硬门槛）        |   /5 | 输入、事件、状态和 DOM 更新路径可解释，错误后可恢复         |
| 调试与验证                           |   /5 | 至少一个边界输入、一次错误定位和一次可重复检查            |
| Git 与解释                           |   /5 | 独立分支、小提交、改动说明和 3 分钟源码讲解               |

### 过关条件

- 总分至少 18；JavaScript/DOM 行为至少 2。
- 仅用键盘可以完成主要操作。
- 能回答事件从哪里触发、状态在哪里改变、DOM 为什么更新。
- 如未通过，先完成“前端基础补救路线”，再补测一个不同输入的相邻任务。

## W7 检查点：能否交付类型化的功能闭环

### 限时任务

在当前 Issue 功能中完成一个小闭环，例如筛选、创建字段、状态更新或错误恢复。至少使用 local 模式完成，若使用 API 必须记录真实数据来源。

| 项目                    | 分值 | 通过证据                                                |
| ----------------------- | ---: | ------------------------------------------------------- |
| 用户旅程                |   /5 | 从入口到结果完整，加载、空、错误至少覆盖两态            |
| TypeScript 与状态       |   /5 | 输入、领域对象、视图状态可区分；没有用断言掩盖错误      |
| 数据 Contract（硬门槛） |   /5 | 请求/响应或 local 数据 shape 有表格，null/省略/枚举清楚 |
| 无障碍与恢复            |   /5 | 键盘可操作、错误可理解、重试或修正后可继续              |
| 测试与证据              |   /5 | 至少一个纯逻辑/组件测试和一份用户旅程证据               |

### 过关条件

- 总分至少 18；Contract 至少 2。
- 能明确说出当前是 local、同源 API 还是 .NET API，不把三者混为一谈。
- 修改一个边界输入后仍能独立修正或解释失败。
- 未通过时执行“TypeScript/Contract 补救路线”。

## W10 检查点：能否管理服务端状态与并发恢复

### 限时任务

实现一个陌生领域的“阅读清单”查询：owner、filter、page 共同组成缓存身份；archive mutation 必须支持乐观更新、失败回滚和乱序并发恢复。不得复用 IssueFlow 的现成 Query Key。

| 项目                         | 分值 | 通过证据                                                   |
| ---------------------------- | ---: | ---------------------------------------------------------- |
| Query Key（硬门槛）          |   /5 | 所有改变身份的输入进入 key；默认值规范化且 shape 不碰撞     |
| fresh/stale 与加载状态       |   /5 | 首次加载、后台刷新、空结果和错误状态可区分                 |
| Mutation 与失效              |   /5 | archive 成功后精准更新并失效相关缓存                        |
| 乐观更新与回滚（硬门槛）     |   /5 | 500 后完整回滚；旧响应不会覆盖较新的成功结果                |
| 测试与解释                   |   /5 | 使用确定性测试覆盖分页、失败和乱序，不使用固定 sleep        |

### 过关条件

- 总分至少 18；Query Key 和回滚均至少 2。
- 能解释每次读取、写入、取消、失效和回滚影响的缓存范围。
- 至少使用一个正文未出现的新 owner/filter 组合验证迁移能力。
- 未通过时执行“测试与调试补救路线”，不得提前进入双后端安全检查点。

## W11 检查点：能否跨越前后端契约与安全边界

### 限时任务

使用课程提供的共享 Contract Suite，对照同源 D1/R2 API 和独立 .NET API。运行全部 18 个既有 case，独立实现或修复其中 4 个，并完成陌生“预约系统”Contract 迁移题。

| 项目                         | 分值 | 通过证据                                               |
| ---------------------------- | ---: | ------------------------------------------------------ |
| 两种真实后端与配置           |   /5 | 请求目标、存储位置、fixture reset 和行为差异可追踪     |
| HTTP/JSON Contract（硬门槛） |   /5 | 方法、状态、JSON shape、null/省略及 204 有共同用例     |
| 后端数据路径                 |   /5 | 能从 Endpoint/Route 追到数据层，并说明持久化边界       |
| 认证与安全（硬门槛）         |   /5 | 401/403/CORS 区分清楚，有非法输入和上传负面证据        |
| 跨层诊断与清理               |   /5 | 用 Problem Details/日志定位失败，隔离数据和文件已清理  |

### 过关条件

- 总分至少 18；Contract 和安全均至少 2。
- 不声称两种实现完全等价；每个差异都有产品决定和回归证据。
- 预约迁移题覆盖省略 note、显式 null、409 时段冲突和 401/403。
- 证据不能包含 Cookie、token、连接串或真实个人数据。
- 未通过时分别走“Contract 补救路线”或“安全补救路线”。

## W12 检查点：能否用测试、调试和 CI 保护交付

### 限时任务

从 IssueFlow 选择一个关键行为，建立单元/API/E2E 中合适的测试组合，制造一次失败，定位并修复，再说明 CI 如何防止回归。

| 项目                | 分值 | 通过证据                                              |
| ------------------- | ---: | ----------------------------------------------------- |
| 单元与契约测试      |   /5 | 测试名称描述行为，覆盖边界，不只验证 happy path       |
| E2E 用户旅程        |   /5 | 角色/名称定位稳定，无任意固定 sleep，有报告或 trace   |
| 系统调试            |   /5 | 复现、假设、事实、根因、修复、回归六步完整            |
| CI 与权限（硬门槛） |   /5 | 本地等价检查可运行，普通 PR 无多余写/部署/secret 权限 |
| 质量证据            |   /5 | 命令、环境、数据模式、失败分类和已知限制可交接        |

### 过关条件

- 总分至少 18；CI 与权限至少 2。
- 至少展示同一条测试修复前失败、修复后通过。
- 至少一个 4xx、非法输入、未授权或文件安全负面路径有自动化保护。
- 等待 runner、构建和浏览器下载的空闲时间未计入 120 分钟。

## 100 分毕业量表

毕业评审使用第 13 周纵向项目。总分达到 **75/100** 才能通过，同时满足硬门槛：

- TypeScript 不得为 0，且建议至少 9/15；
- Contract 不得为 0，且建议至少 9/15；
- 安全与可靠性不得为 0，且建议至少 6/10；
- 没有提交 secrets、伪造测试结果或覆盖他人未授权改动；
- Must 范围存在可运行证据。

| 类别                          |    分值 | 高分证据                                                                       |
| ----------------------------- | ------: | ------------------------------------------------------------------------------ |
| 用户价值与完整功能            |      20 | 问题明确；正常、空、错误、恢复状态完整；Must 全部交付                          |
| TypeScript（硬门槛）          |      15 | 领域/请求/响应/视图类型清楚；null/省略明确；边界有运行时保护；无无理由 `any`   |
| API 与数据 Contract（硬门槛） |      15 | 方法、状态、Problem Details、JSON shape 和数据模式差异可追踪，有成功与失败证据 |
| 测试、调试与 CI               |      20 | 风险驱动的多层测试、红绿回归、根因记录、最小权限 CI/等价质量闸门               |
| 无障碍与 UI 状态              |      10 | 语义控件、键盘、焦点、名称、响应式、颜色以外信息和恢复路径                     |
| 安全与可靠性（硬门槛）        |      10 | 身份/权限决策、输入校验、错误脱敏、负面测试、竞态/失败处理和剩余风险           |
| 文档、Git 与演示证据          |      10 | 范围/架构/限制清楚，小提交，证据索引完整，5 分钟内可复现价值                   |
| **总分**                      | **100** |                                                                                |

### 总分判定

- **90–100：优秀通过。** 能独立交付并审查一个小型纵向切片。
- **75–89：通过。** 核心闭环可靠，薄弱项已有具体后续计划。
- **60–74：暂缓毕业。** 保留已完成项目，执行 1–2 条补救路线后补评。
- **0–59：未通过。** 回到最近通过的检查点，缩小项目范围并重建证据。
- **硬门槛失败：** TypeScript、Contract、安全任一项为 0，或出现秘密泄露/伪造证据时，无论总分都不通过。

## 补救路线

补救不是重复观看整周。每条路线都包含诊断、针对性练习和一个不同输入的补测。完成后用新证据替换原 0–2 分证据。

### 路线 A：概念和源码追踪

适用症状：能运行但说不出入口、数据来源和失败去向。

1. 选择一个按钮或请求，画“用户动作 → 组件 → 状态/API → 数据层 → UI”的链路。
2. 每层只回答输入、输出、失败、测试四个问题。
3. 关闭源码，用空白纸重画并录制 3 分钟讲解。
4. 补测证据：导师/同伴随机指定相邻行为，10 分钟内指出关键文件和验证点。

### 路线 B：TypeScript

适用症状：大量 `any`、双重断言、null/省略混淆、泛型被当作运行时校验。

1. 在 TypeScript Lab 重做 union、narrowing、generic、unknown 与运行时守卫示例。
2. 从毕业项目选一个 JSON 边界，把输入先视为 `unknown`，完成最小验证或可靠解析。
3. 为 null、属性省略和未知枚举各写一个测试。
4. 补测证据：在不看答案时为一个新字段完成类型、解析、错误与测试。TypeScript 分仍为 0 时不得毕业。

### 路线 C：API 与数据 Contract

适用症状：只写 TypeScript interface，没有真实响应；混淆 local、同源和 .NET；忽略 204/4xx。

1. 建立“方法—路径—输入—成功状态—失败状态—JSON shape—实现模式”矩阵。
2. 抓取一条真实成功和失败响应，逐字段与类型对照。
3. 比较至少两种数据模式，标出一个行为差异或未验证项。
4. 补测证据：新增一个错误状态的客户端/后端测试，并让 UI 呈现可行动错误。Contract 为 0 时不得毕业。

### 路线 D：安全与可靠性

适用症状：把 CORS 当认证、只测成功、日志含凭据、客户端输入被直接信任。

1. 画信任边界，列出身份、输入、存储、跨源和错误信息五类风险。
2. 从未授权、非法枚举、重复写入、伪造上传、竞态中选择两个负面实验；只在隔离环境进行。
3. 检查截图、日志、提交和 CI artifact，删除 secrets 与个人数据。
4. 补测证据：一个自动化负面测试、一份脱敏结果和剩余风险。安全分为 0 时不得毕业。

### 路线 E：测试与调试

适用症状：测试只断言页面存在、E2E 靠固定等待、修复没有回归测试。

1. 为同一行为分别列出单元、集成、E2E 可以发现的风险，选择最小组合。
2. 故意制造故障，保存失败输出。
3. 按“复现—假设—事实—根因—修复—回归”完成记录。
4. 补测证据：同一条测试红灯到绿灯，并连续运行关键 E2E 两次。

### 路线 F：无障碍与 UI 状态

适用症状：点击 `div`、焦点不可见、只用颜色、错误后无法继续。

1. 仅用键盘走完主要旅程，记录第一处阻塞。
2. 检查语义、可访问名称、焦点、错误关联与状态通知。
3. 制造加载、空、错误和重试四态。
4. 补测证据：键盘步骤、四态截图和一个角色/名称定位的自动化断言。

### 路线 G：Git、证据与范围控制

适用症状：一个巨大提交、证据不可定位、未完成项被隐藏、范围持续膨胀。

1. 把任务缩成不超过 5 个 Must，明确非目标。
2. 在独立分支完成“失败测试—实现—整理”三个小提交。
3. 建立证据索引，包含命令、环境、数据模式、结果和已知限制。
4. 补测证据：另一个人仅凭索引在 15 分钟内复现核心结果。

## 补评规则

- 在原评分表旁保留第一次分数和原因，不覆盖历史。
- 补救必须使用新的或变化后的输入，不能原样背诵同一道题。
- 只补评未通过维度；其余分数保持，除非新改动破坏了原证据。
- 补评仍需记录提示等级。4 级提示完成的任务还要再做一次无提示迁移。
- 同一硬门槛连续两次为 0，回到最近一次通过的阶段检查点，并把毕业项目范围缩小一半。
