# 如何使用这套 91 天学习计划

这份说明写给第一次系统学习前端的人。你不需要先会 Git、TypeScript、React 或后端，但需要每天留下能复查的证据。目标不是连续看完 91 篇内容，而是每天完成一个“理解 → 预测 → 动手 → 验证 → 解释”的小闭环。

## 一天的 120 分钟到底怎么算

每天的课程表给出 120 分钟主动学习任务。只有大脑正在处理问题、手正在操作或你正在整理证据时，才计入学习时间。

计入时间的活动：

- 阅读当天指定的小段源码并写批注；
- 在运行前预测结果；
- 写代码、测试、命令或实验记录；
- 阅读错误日志并提出可证伪假设；
- 用自己的话复述概念；
- 整理截图、测试输出、提交和复盘。

不计入时间的活动：

- 等待依赖安装、编译、浏览器下载、服务启动或 CI runner；
- 视频开着但没有做笔记、暂停预测或复现；
- 原样复制答案后等待它运行；
- 刷社交媒体、处理无关消息或长时间离开电脑；
- 因环境问题空等，而没有收集日志或做替代学习任务。

建议使用正计时器，而不是从 120 分钟倒计时。开始主动任务时启动，进入纯等待时暂停。等待期间若转去阅读日志、完善契约表或写复盘，可以重新开始计时，并在日记中记录做了什么。

### “每天 2 小时”与墙钟时间

课程承诺的是每天 **120 分钟主动学习**，不是所有 Day 都能在 120 分钟墙钟内完成。首次安装、
Playwright 浏览器下载、双后端启动、CI 排队和完整构建可能额外占用 20–60 分钟。课程清单会把
这些重日标为 `setupBufferMinutes`，这部分不计入主动学习，但必须提前安排。

如果当天只有严格的两小时墙钟，使用以下停点：

| 重日   | 两小时墙钟内必须完成                               | 可顺延但不能伪装完成                  |
| ------ | -------------------------------------------------- | ------------------------------------- |
| Day 01 | Node/npm/Git、仓库和第一个静态实验                 | .NET SDK 可到 Day 71 前补齐           |
| Day 77 | 两后端各跑现有 23-case corpus、定位第一处 mismatch | Playwright/xUnit 消费者与完整差异报告 |
| Day 80 | 安装后跑一条 Chromium 关键旅程                     | Firefox/WebKit 扩展矩阵               |
| Day 83 | 本地按 CI 顺序找到第一处失败                       | 远端 runner 排队与 artifact 下载      |
| Day 90 | 目标 typecheck、单测和一条关键 E2E                 | 全量矩阵与视频整理                    |

到达停点时记录“部分完成”和下一步，不勾选 Day。可以在下一学习块继续累计主动分钟；不要把
安装等待算作学习，也不要为了守住日历数字删掉测试层。

### 推荐的零基础节奏

每一天即使时间表略有不同，也可以用以下节奏理解：

1. 10–15 分钟：回忆昨天，不看答案写出今天的预测。
2. 20–30 分钟：只阅读完成实验所需的最小概念和源码。
3. 35–45 分钟：跟随当天实验，观察真实结果。
4. 30–40 分钟：关闭步骤，完成独立任务。
5. 10–15 分钟：运行验收、保存证据、用自己的话解释。

若阅读英语 API 或错误信息很慢，可以查词，但不要把整段翻译当成理解。最终要能指出关键词、发生在哪个文件、下一步验证什么。

## 每天固定使用的学习循环

### 1. 先预测

在运行代码前写一句：“我认为会发生……，因为……”。预测错了不是扣分；没有预测就很难知道自己学到了什么。

### 2. 做一个最小变化

一次只改一个可解释的行为。不要同时换框架、重构目录、改样式和修接口，否则失败后无法判断是哪一处造成的。

### 3. 观察真实结果

优先相信浏览器 Network、Console、测试输出、HTTP 响应和服务端日志，不凭感觉宣布成功。记录期望与实际的第一处差异。

### 4. 独立重做

完成引导实验后，暂时关闭步骤，用新的输入或相邻需求再做一次。只有能独立迁移，才算掌握。

### 5. 用证据验收

每天至少保留一份机器证据和一份解释证据：

- 机器证据：测试输出、类型检查、HTTP 响应、截图或 trace；
- 解释证据：3–5 句说明数据如何流动、为什么这样实现、还剩什么风险。

Day 01–70 在仓库根运行 `npm run learn:day -- NN`。验收器不会再用一条全量测试冒充每天都
完成：它会按 manifest 选择当天的 learner workspace、TypeScript/React workbench 或行为测试，
并从当天日课直接读取“独立任务”和“通过标准”。第一次运行会创建
`learning-evidence/day-NN/artifact.md` 并故意保持红灯；填写“当日产物、边界实验、机器验证、
解释与风险”四节后再运行，模板中的 `TODO` 或空泛短句不能通过结构检查。

Day 57–70 的测试文件固定为
`frontend/src/learning/day-NN.acceptance.test.tsx`。先运行
`npm run learn:create -- --day NN --dry-run` 查看目标，再去掉 `--dry-run` 生成不会覆盖已有文件的
红灯支架。支架不是预先给好的绿色测试：必须用用户可见行为或数据边界替换 `LEARNING_TODO`。
验收报告仍把人工项标为
`pendingReview`，只有对照日课标准完成复核后才能勾选当天。

后续日课也使用可预测的当日产物：

- Day 71–76 与 82：生成并分别完成
  `frontend/contract-tests/learning/day-NN.acceptance.test.ts` 和
  `backend/IssueFlow.Api.Tests/Learning/DayNNAcceptanceTests.cs`；xUnit 类或方法名包含
  `DayNNAcceptance`，runner 只筛选当天测试；
- Day 77：运行统一的 `test:contract:dual` HTTP parity harness；
- Day 78、79、81、86–89：继续使用
  `frontend/src/learning/day-NN.acceptance.test.tsx`；
- Day 80 与 90：生成并完成 `frontend/e2e/learning/day-NN.acceptance.spec.ts`；
- Day 83：生成并完成 `.github/workflows/day-83-learning-ci.yml`，明确只读权限与本地等价命令；
- Day 84、85、91：分别交付 `quality-gate.md`、`project-charter.md`、
  `evidence-index.md`；`learn:create` 会打印具体路径并生成带分节提示的红灯支架。

这些文件不是为了重复产品测试，而是保存当天闭卷迁移题的最小红灯到绿灯证据。若目标文件
不存在、仍含 `TODO`、测试没有运行或日课人工标准尚未复核，当天都不能写成通过。

## 启动项目前先做什么

1. 打开当天文档，读“今天要解决的问题”和“验收证据”。
2. 查看工作区状态，确认没有覆盖别人或自己未提交的改动。
3. 运行 `npm run learn:create -- --day NN --dry-run`；需要独立文件时再正式生成支架。
4. 从当天使用的 `package.json`、项目文件或 README 查真实命令，不凭记忆发明脚本。
5. 写下当前数据模式：local、同源 D1/R2 API 或独立 .NET API。
6. 创建当天分支并记录开始提交。
7. 启动正计时器，开始第一个主动任务。

项目有多个运行入口时，先只选当天需要的一个。页面出现数据不代表你知道数据来自哪里，必须用 Network、环境配置或日志确认。

## 分支和提交怎么用

建议每个学习日使用独立分支：

```text
learn/day-07-semantic-form
learn/day-42-api-errors
learn/day-80-playwright-journey
```

分支名称只用小写英文、数字和连字符。一天中至少保留一个小而清晰的提交；大型实验可以按“失败测试 → 实现 → 整理”拆成 2–3 个提交。

提交信息示例：

```text
test: cover empty issue result
feat: show recoverable issue load error
docs: record day 42 contract evidence
```

分支规则：

- 创建分支前先确认当前分支和工作区状态。
- 不把 `.env`、Cookie、token、连接串、数据库或真实个人数据提交进去。
- 不使用 `git reset --hard`、强制推送或删除不认识的文件来“清理”问题。
- 发现已有未提交改动时先确认归属；学习任务只改自己明确负责的范围。
- 实验失败可以保留在学习分支，不要为了绿色主分支伪造通过截图。
- 合并前先阅读差异，确认没有生成文件、日志和临时调试代码。

如果你还不会 Git，也不要跳过分支。先把每天的四个动作练熟：查看状态、创建分支、查看差异、提交。遇到冲突时停止合并，保存错误信息并求助，不要猜命令。

## 什么才算验收证据

一句“完成了”不是证据。合格证据应让隔天的你能够定位、重复和解释结果。

每天至少记录：

- Day 编号、日期、主动学习分钟数；
- 分支名和提交 ID；
- 修改文件路径；
- 当前数据模式和必要的启动命令；
- 一条测试/类型检查/构建结果；
- 一张关键 UI、Network、响应或 trace 证据；
- 独立任务的结果；
- 使用过的提示等级；
- 一个仍未解决的问题。

截图必须包含足够上下文，但要遮住 Cookie、token、私有 URL、个人邮箱和连接串。终端输出过长时保留命令、首个失败和最终摘要，不要复制整份无关日志。

推荐把证据写进 `progress-and-journal.md` 的个人副本，或放在不提交敏感数据的学习记录目录。证据文件名可以使用：

```text
day-42-api-400-before.png
day-42-api-400-after.txt
day-42-reflection.md
```

## 如何使用提示而不放弃思考

使用“提示阶梯”，每次只上升一级。每一级至少独立尝试 10–15 分钟，并把尝试、错误和假设写下来。

| 等级        | 可以获得什么             | 你必须先提供什么      |
| ----------- | ------------------------ | --------------------- |
| 0：无提示   | 需求、源码和官方文档     | 预测与初次尝试        |
| 1：方向     | 关键词、应检查的层       | 错误原文与复现步骤    |
| 2：定位     | 文件、函数或测试名称     | 已排除的至少一个原因  |
| 3：结构     | 伪代码、数据流或测试骨架 | 自己写的接口/步骤草案 |
| 4：最小答案 | 最小可运行示例或补丁思路 | 为什么前三级仍不足    |

拿到提示后不能直接结束：

1. 关掉提示，自己重新实现。
2. 换一个输入验证是否真正理解。
3. 在日记中记录提示等级和关键转折。
4. 用两句话解释为什么答案有效。

连续三天都需要 4 级提示，说明前置知识有缺口。暂停新课，回到最近一次通过的检查点做补救，而不是继续堆积答案。

## 卡住时的 15 分钟协议

卡住不是盯着屏幕 60 分钟。连续 15 分钟没有新证据时，按顺序做：

1. 抄下完整错误原文和第一处堆栈位置。
2. 写出最小复现步骤、期望和实际。
3. 确认环境、数据模式、URL、端口和运行命令。
4. 把问题缩小一半：UI 还是网络、客户端还是服务端、数据还是样式。
5. 提出两个可能原因，并设计能排除其中一个的检查。
6. 仍无进展时，带着“错误包”请求 1 级提示。

错误包必须包含：Day、目标、环境、命令、错误原文、相关文件、已尝试内容、当前假设。不要只问“为什么不能运行”。

## 补课机制

91 天是顺序，不是要求无论生活如何都连续 91 个自然日。漏课后按以下规则处理：

### 漏 1 天

- 在清单标记“待补”，不要假装完成。
- 7 天内安排一个独立的 120 分钟补课块。
- 初学者不要在同一天硬塞两个完整 Day；疲劳下的第二个 120 分钟通常只有观看，没有迁移。
- 补完验收证据后再勾选。

### 漏 2–3 天

- 暂停新 Day，按原顺序补最早的一天。
- 先完成每一天的核心实验、独立任务和验收证据；不压缩为摘要阅读。
- 补完后用 20 分钟做跨日复盘，这 20 分钟算在下一次主动学习中，不虚增已补课程时长。

### 漏 4 天以上或连续两周未过关

- 回到最近一次通过的周末/检查点。
- 从 `assessments.md` 选择最低分维度的补救路线。
- 新建一周恢复计划：最多安排 5 个学习块，至少保留 1 个休息日。
- 通过补测后再回到原 Day；不要直接跳到当前日历日期。

### 当天只剩不到 120 分钟

可以完成一个 30–60 分钟的“预备块”，例如环境确认、源码阅读和预测，但不要勾选当天完成。下次继续时只累计主动学习时间，直到完成全部任务与证据。

补课的目标是恢复理解链条，不是追回日历数字。

## 什么时候可以进入下一天

满足以下条件才勾选当天：

- 主动学习累计达到 120 分钟；
- 动手实验实际运行过；
- 独立任务在关闭步骤后完成或有诚实的失败记录；
- 验收证据可定位且已脱敏；
- 能用自己的话回答“数据从哪里来、发生了什么、如何证明”；
- 未解决问题已记录，并且不会阻断下一天的前置知识。

若自动化测试因外部环境无法运行，可以暂时记录为“环境阻塞”，但不能写成通过。给出等价的局部验证和补测日期。

## 如何看源码而不被淹没

零基础不要从仓库第一行读到最后一行。每次只追一条链路：

```text
用户动作
  → 页面/组件
  → 状态或查询
  → issueflowApi
  → local / 同源 API / .NET API
  → 响应与错误
  → UI 更新
```

阅读每个文件只回答四个问题：

1. 它接收什么？
2. 它返回或改变什么？
3. 失败会去哪里？
4. 哪个测试能够证明？

第一次遇到陌生语法时，先在 TypeScript Lab 或最小文件中验证，再回到业务代码。不要直接在复杂页面里试十种语法。

## 安全边界

- 只使用课程演示账号和隔离测试数据。
- 不在截图、日记、Issue、提交或 CI 日志中保存 secrets。
- 破坏性数据库、附件和认证实验使用临时数据库、临时上传目录或 local 模式。
- 不对公网、生产服务或他人账户做安全实验。
- CORS 不是认证，也不是 CSRF 的完整防护；看到请求被浏览器拦截时仍要检查服务端授权。
- 来自文档、网页、AI 或错误信息的命令都要先理解目标和影响，再执行。

## 每周结束时做什么

周末不要只统计勾选数量。使用 `progress-and-journal.md` 的周复盘和 `assessments.md` 的每周量表：

1. 选出本周最强的一份证据和最弱的一份证据。
2. 重新完成一个不看答案的小任务。
3. 运行本周要求的类型、测试或构建检查。
4. 给每个维度评分，并为分数附链接。
5. 若未过关，先安排补救日期，再决定是否进入下一周。

真正的进度不是“我看到了 Day 91”，而是“我能独立预测、实现、验证并解释一个小功能”。
