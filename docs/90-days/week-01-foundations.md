# 第 1 周：环境、工具与 Web 地图

本周用 14 小时建立之后 12 周都依赖的操作基线。你不会急着写 React，而是先确认：
代码在哪里运行、浏览器看见了什么、请求怎样流动、修改如何被 Git 记录。

## 本周完成标准

- 能从空终端启动 IssueFlow，并解释每条命令在哪个目录执行；
- 能使用浏览器 Elements、Console、Network、Application 四个面板；
- 能画出登录请求从表单到 API、Cookie、页面跳转的完整链路；
- 能区分当前项目的同源 API、.NET API 和 localStorage 演示模式；
- 能创建学习分支、阅读 diff，并提交一个不混入无关文件的小改动。

本周交付物：`notes/week-01-web-map.md`。如果仓库中没有 `notes`，可先在仓库外
记录，完成本周后再决定是否提交个人学习日志。

## Day 01：建立可重复的运行基线 {#day-01}

### 今日目标

理解“项目能运行”不是看到一个页面，而是能重复安装依赖、启动服务、打开正确 URL，
并记录版本与错误。

### 120 分钟安排

| 时间    | 任务                                                              |
| ------- | ----------------------------------------------------------------- |
| 0–15    | 写下你认为 Node、npm、浏览器和前端项目各自负责什么                |
| 15–40   | 阅读[开始之前](../learning/00-getting-started.md)的环境与目录部分 |
| 40–80   | 检查版本、安装依赖、启动前端并登录                                |
| 80–110  | 关闭终端后重新启动一次，故意在错误目录运行命令并解释报错          |
| 110–120 | 记录版本、启动 URL、成功标志和一个未理解的问题                    |

### 动手实验

在仓库根目录执行：

```powershell
npm run learn:check -- --day 01
git status --short
```

此时 Node、npm 和 Git 是硬门槛；.NET SDK 10 缺失只显示 `WARN`。若已安装可以额外记录
`dotnet --version`，若未安装则写下第 10 周结束前的安装日期，不要让后端工具阻断第一周。

进入前端目录后执行：

```powershell
cd frontend
npm install
npm run dev
```

观察终端给出的 URL，而不是凭记忆猜端口。浏览器打开页面后完成登录、进入 Issues
列表、打开一条 Issue，再回到 Dashboard。

### 独立变体

停止开发服务器，回到仓库根目录直接执行 `npm run dev`。记录错误或脚本差异，
然后解释为什么“命令正确”还不够，工作目录也是输入的一部分。

### 当日证据

- Node、npm 和 Git 版本；若已有 .NET 则记录版本，否则保留 `WARN` 与 Day 71 前安装计划；
- 正确启动命令及工作目录；
- 登录后经过的三个页面；
- 错误目录实验的原始错误和你的解释。

### 验收问题

- [ ] 能说出仓库根 `package.json` 与 `frontend/package.json` 的职责差异。
- [ ] 能说明开发服务器停止后浏览器为什么不能继续加载新页面。
- [ ] 没有把 `node_modules` 加入 Git。

## Day 02：用 Git 保存可解释的学习过程 {#day-02}

### 今日目标

掌握 `status → diff → add → commit` 循环，理解工作区、暂存区和提交不是同一个状态。

### 120 分钟安排

| 时间    | 任务                                               |
| ------- | -------------------------------------------------- |
| 0–15    | 不查资料画出工作区、暂存区、HEAD 三个盒子          |
| 15–40   | 查看当前分支、最近提交和忽略规则                   |
| 40–80   | 创建学习分支，修改一段无风险文案并观察三种 diff    |
| 80–110  | 撤销自己的实验或提交到学习分支，确认主分支未被污染 |
| 110–120 | 用五句话写出你的 Git 提交流程                      |

### 动手实验

```powershell
git branch --show-current
git log -5 --oneline
git status --short
git diff
git diff --staged
```

选择一个只影响显示的文案，在独立分支修改。先看 `git diff`，暂存后再次比较
`git diff` 与 `git diff --staged`。不要修改历史存档目录。

### 精讲：为什么学习实验也需要小提交

当实验包含 HTML、CSS、TypeScript 和测试四种变化时，一次大提交会让你无法判断
哪一步改变了行为。小提交相当于实验记录：每个提交只回答一个问题，并保存当时通过的
验证命令。

### 独立变体

创建第二处改动，但只暂存第一处。使用 `git status --short` 解释两行状态字符，
证明你知道什么将进入下一次提交。

### 验收问题

- [ ] 能解释 `git diff` 为什么看不到已暂存的内容。
- [ ] 能在不删除他人改动的前提下只处理自己的文件。
- [ ] 提交信息描述了结果，而不是“update”或“test”。

## Day 03：从 URL 到屏幕 {#day-03}

### 今日目标

建立浏览器、URL、HTTP、HTML/CSS/JavaScript、React 和 DOM 的第一张因果图。

### 120 分钟安排

| 时间    | 任务                                                          |
| ------- | ------------------------------------------------------------- |
| 0–15    | 写下在地址栏按 Enter 后你认为发生的五件事                     |
| 15–40   | 阅读[浏览器与 Web](../learning/02-browser-and-web.md)前半部分 |
| 40–80   | 使用 DevTools 检查 Document、JS、CSS 请求与最终 DOM           |
| 80–110  | 禁用 JavaScript或网络缓存，比较页面行为                       |
| 110–120 | 修正最初的五条预测，画出新流程                                |

### 观察路径

1. 打开 DevTools Network，勾选 Preserve log；
2. 刷新登录页，按 Type 排序；
3. 找到 Document 请求，记录 URL、status、content-type；
4. 打开 Elements，找到登录表单；
5. 在 Sources 或 Network 中找到加载的 JavaScript；
6. 比较“服务器返回的 HTML”和 React 更新后的 DOM。

### 独立变体

在 DevTools 中临时修改一个按钮文字和 CSS。刷新页面后观察修改消失，并解释：
Elements 面板改的是当前内存中的 DOM，不是磁盘源码。

### 验收问题

- [ ] 能区分 HTML 源文本、DOM 和 React 组件代码。
- [ ] 能解释为什么刷新会清除 DevTools 中的临时 DOM 修改。
- [ ] 流程图至少包含 URL、请求、响应、JavaScript、DOM 和绘制。

## Day 04：读懂一次 HTTP 请求 {#day-04}

### 今日目标

能从 Network 面板解释 method、status、header、body、Cookie 和重定向。

### 120 分钟安排

| 时间    | 任务                                                              |
| ------- | ----------------------------------------------------------------- |
| 0–15    | 回忆 GET 与 POST 的差异，并写下 200/400/401/404/500 的猜测        |
| 15–40   | 阅读[浏览器与 Web](../learning/02-browser-and-web.md)的 HTTP 部分 |
| 40–80   | 捕获一次成功登录和一次失败登录                                    |
| 80–110  | 比较两个请求的 payload、status、response 与后续导航               |
| 110–120 | 写一张“看到某状态码先查什么”的表                                  |

### 请求对照表

| 观察项          | 成功登录           | 失败登录           |
| --------------- | ------------------ | ------------------ |
| Method          | 记录实际值         | 记录实际值         |
| Request URL     | 完整 URL           | 完整 URL           |
| Status          | 记录并解释         | 记录并解释         |
| Request payload | 哪些字段离开浏览器 | 是否相同           |
| Response        | 返回了什么 shape   | 错误采用什么 shape |
| Cookie          | 哪一步设置或携带   | 是否发生变化       |
| 页面结果        | 跳到哪里           | 错误显示在哪里     |

### 独立变体

开启 Offline 后再次提交。区分“服务器返回错误”和“请求根本没有到达服务器”：
它们在 status、response 和前端提示上有什么不同？

### 验收问题

- [ ] 不把 HTTP 401 与前端页面重定向混为一谈。
- [ ] 能指出请求 body 与 response body。
- [ ] 能解释 Offline 为什么可能没有 HTTP status。

## Day 05：建立项目目录地图 {#day-05}

### 今日目标

知道修改页面、业务组件、API client、同源 API、.NET API 和测试时分别去哪里找。

### 120 分钟安排

| 时间    | 任务                                                                   |
| ------- | ---------------------------------------------------------------------- |
| 0–15    | 不打开文档，猜测 `frontend/app` 与 `frontend/src` 的职责               |
| 15–40   | 阅读[项目地图与数据模式](../learning/01-project-map-and-data-modes.md) |
| 40–80   | 从登录页面沿 import 和调用追踪到 API                                   |
| 80–110  | 从 Issues 页面选择一个按钮，列出 UI 到测试的文件路径                   |
| 110–120 | 完成一张“需求类型 → 首先查看的目录”表                                  |

### 必须找到的入口

- 应用布局与页面入口；
- Provider 组合；
- 屏幕级组件；
- Issue 领域类型；
- API client；
- 同源 route handler；
- .NET endpoint；
- 单元/组件测试与 E2E。

不要试图逐行读完整仓库。先问“当前行为的所有者是谁”，再沿 import、函数调用和
HTTP 路径逐层缩小范围。

### 独立变体

选择“修改 Issue 状态”功能，写出至少六个可能相关文件。然后使用
[源码追踪路线](../reference/source-traces.md)核对，标记猜对和遗漏的原因。

### 验收问题

- [ ] 能解释 `app`、`src/screens`、`src/features` 和 `src/server` 的边界。
- [ ] 能找到一个功能对应的前端测试和后端测试。
- [ ] 文件地图按职责组织，而不是只复制目录树。

## Day 06：理解三种数据模式 {#day-06}

### 今日目标

区分同源 D1/R2、独立 .NET/SQLite 和 localStorage 演示模式，理解环境变量怎样改变
请求路径。

### 120 分钟安排

| 时间    | 任务                                                                           |
| ------- | ------------------------------------------------------------------------------ |
| 0–15    | 预测三种模式的数据分别保存在哪里                                               |
| 15–40   | 精读[项目地图与数据模式](../learning/01-project-map-and-data-modes.md)对应章节 |
| 40–80   | 检查环境变量示例、API base 计算和 local 模式分支                               |
| 80–110  | 至少运行默认模式与 local 模式，比较 Network 和持久化                           |
| 110–120 | 画出三列对照图并记录切换时必须重启的原因                                       |

### 对照维度

| 维度         | 同源 API     | .NET API         | local 模式          |
| ------------ | ------------ | ---------------- | ------------------- |
| 前端请求 URL | 观察         | 观察             | 是否发请求          |
| 数据位置     | D1/R2 兼容层 | SQLite/上传目录  | 浏览器 localStorage |
| 认证         | 观察 Cookie  | 观察 Cookie/CORS | 演示身份            |
| 清空数据方式 | 查文档       | 查数据库路径     | 清 localStorage     |
| 适合用途     | 集成         | 后端对照         | 纯前端教学          |

### 独立变体

在 local 模式创建一条 Issue，刷新并重启开发服务器，记录数据是否存在。再清理对应
localStorage key，解释“刷新”“重启服务器”“清浏览器存储”为什么是三种不同操作。

### 验收问题

- [ ] 能说出 local 模式为什么不能证明真实 API 正确。
- [ ] 能解释同源请求为何通常不需要完整 origin。
- [ ] 知道切换公开环境变量后为什么需要重启开发服务器。

## Day 07：周测、故障演练与复盘 {#day-07}

### 今日目标

在没有逐步提示的情况下恢复项目、追踪一个请求并交付本周证据。

### 120 分钟安排

| 时间    | 任务                                     |
| ------- | ---------------------------------------- |
| 0–20    | 闭卷回答本周十个问题                     |
| 20–50   | 从空终端启动项目并完成登录               |
| 50–80   | 故意制造一个端口/环境变量/网络错误并定位 |
| 80–105  | 完成登录请求链路图和三种数据模式图       |
| 105–120 | 自评、整理证据并安排下周补救             |

### 闭卷问题

1. npm script 在哪里定义？
2. 工作目录为什么会改变同一条命令的结果？
3. HTML 源码和 DOM 有何区别？
4. Network 中没有 status 可能意味着什么？
5. 401 与 403 的含义有何不同？
6. Cookie 在请求与响应中分别怎样出现？
7. screen 与 feature 组件的职责怎样区分？
8. 同源 API 与 .NET API 的 base URL 有何差异？
9. localStorage 演示模式不能验证什么？
10. Git 暂存区解决了什么问题？

### 故障卡

随机选择一个，不看答案完成：

- 在错误目录启动；
- 占用预期端口；
- 打开 Offline；
- 写错 API base；
- 保留过期 localStorage 数据；
- 修改页面后忘记保存文件。

记录：症状 → 三个假设 → 最便宜的验证 → 根因 → 修复 → 防复发方法。
